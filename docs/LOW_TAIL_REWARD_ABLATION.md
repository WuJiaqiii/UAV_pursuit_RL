# 02_low_tail reward and transfer-BC experiment

## Motivation

The latest run used `progress=6`, but the second-stage Actor still produced
only 1/64 and 0/64 safe entries on its two final gate seeds. The uploaded
run summary also shows that the second-stage run performed **zero BC updates**:
`init_from` loaded the parent Actor and skipped the fresh-BC branch. The
completed-episode aggregate is misleading because the 26/64 replay slots
were allocated to the static task twice: `recent` and `anchor` had the same
fingerprint. The new mixture logic deduplicates identical replay profiles,
so the intended mix is 80% current `02_low_tail`, 20% retained `01_static`.

## Reward accounting clarification

The existing environment already multiplies the per-physics reward returned
to PPO by `reward.scale`; therefore the prior hypothesis that PPO received
unscaled reward was incorrect. The actual ambiguity was that the episode
diagnostic accumulator was raw/unscaled while reward-component diagnostics
and PPO rollouts were scaled. The refactor makes raw and scaled accumulators
explicit, forms the returned reward by summing the scaled component tensors,
and checks that the per-decision component sum equals the reward received by
PPO. The scale is **not** applied twice.

For a decision interval containing 10 physics substeps, the returned decision
reward and component totals are both discounted by `physics_gamma` across
those substeps. Per-episode `return_scaled` and `return_unscaled` are
undiscounted sums at the 1 kHz physics rate; evaluation's MC return remains
discounted at the 100 Hz decision rate. These quantities have different
definitions and are named/documented accordingly.

## Hard constraints versus soft shaping

The following are hard terminal/acceptance rules and are **never disabled**
by any ablation:
- first intersection with the 0.5 m target sphere;
- relative speed at first intersection no greater than 15 m/s;
- 2.5g total specific thrust limit, 60 m/s pursuer speed limit;
- configured tilt, workspace, altitude and target-validity constraints;
- timeout and unsafe-entry terminal failures.

The reward terms are soft shaping only:
- `progress`: bounded distance-potential difference;
- `braking`: penalty for closing speed above the distance-dependent
  stopping-speed envelope;
- `entry_velocity`: near-target relative-velocity penalty;
- `tilt`, `rate`, `action_derivative`, `time`: regularization/time costs;
- `completion_bonus` and `failure`: terminal rewards, retained in every run.

Zeroing `braking` or `entry_velocity` does **not** relax the 15 m/s hard
entry-speed gate. It only removes that soft training signal. The
`progress_only_diagnostic` variant removes all soft regularizers while
retaining progress, terminal success and terminal failure. It is a diagnostic,
not a proposed final reward.

## Transfer BC

For each run, the parent `01_static` checkpoint initializes the Actor and
other compatible network weights. When `bc_updates > 0`, DAgger-style
adaptation samples states visited by the inherited Actor in the current
`02_low_tail` environment, labels those states with the **PD teacher**, and
updates the Actor only. A deterministic 32-episode initialization check must
reach at least 50% safe entries before PPO begins. The Critic is then refit
from Monte Carlo returns generated by the adapted Actor. Teacher actions are
never blended into PPO execution.

Reward changes are permitted for weight transfer only; action, observation,
physics, predictor and network contracts must remain identical. The Critic
is recalibrated because the value target changes with the reward.

## Ablation matrix

All variants use the same parent checkpoint, task, seeds, replay ratio,
training budget and validation protocol.

| Variant | BC updates | Change from progress=6 baseline |
|---|---:|---|
| `baseline_pd_bc` | 500 | progress=6, braking=0.5, entry_velocity=0.5 |
| `baseline_no_bc` | 0 | Isolates the value of transfer BC |
| `progress_3_pd_bc` | 500 | progress=3 |
| `progress_0p3_pd_bc` | 500 | progress=0.3 |
| `no_progress_pd_bc` | 500 | progress=0; negative control retaining terminal success/failure |
| `no_braking_pd_bc` | 500 | braking=0 |
| `no_entry_velocity_pd_bc` | 500 | entry_velocity=0 |
| `no_braking_no_entry_velocity_pd_bc` | 500 | Both near-target shaping terms off |
| `no_tilt_regularizer_pd_bc` | 500 | tilt=0; hard tilt limit remains |
| `no_rate_regularizer_pd_bc` | 500 | rate=0 |
| `no_action_smoothness_pd_bc` | 500 | action_derivative=0 |
| `no_time_penalty_pd_bc` | 500 | time=0; hard deadline remains |
| `progress_only_diagnostic_pd_bc` | 500 | All soft regularizers off |

## Budget and evaluation

Screening defaults to the nine primary variants listed in `default_screening_variants`; the remaining regularizer ablations are available by explicit `--variants`. Screening: one seed (42), 4 million aggregate physics steps, 32-episode
validation every 1 million steps, 8 MC episodes, 400 Critic warm-up updates, no periodic MC correction,
and 64-episode final reports on two held-out seed offsets, plus static-task retention checks on two additional seed offsets.

Full confirmation: seeds 42/43/44, 20 million aggregate physics steps per run,
32-episode validation every 4 million steps, 16 MC episodes, 600 Critic
warm-up updates, 16-step MC Critic corrections every 32 PPO updates, and 128-episode final reports on each of two held-out current-task seeds and two retained-static-task seeds.
PPO training physics steps, imitation interactions, MC interactions and
validation interactions are recorded separately. Screening is for ranking
only; do not claim a method passes the curriculum from one seed.

Prediction online updates are disabled for this constant-velocity task to
avoid spending compute fitting a predictor that is not needed for the
current experiment. Predictor architecture/observation contract is unchanged.

## Run

First update the local repository and install it in editable mode. Then:

```bash
python scripts/run_reward_ablation.py \
  --parent-checkpoint runs/v8_curriculum/01_static/seed_42/checkpoints/best_feasible.pt \
  --out runs/low_tail_reward_ablation_screen \
  --stage screening --device cuda
```

After reviewing `ablation_matrix.json`, select the strongest two or three
variants and run full confirmation:

```bash
python scripts/run_reward_ablation.py \
  --parent-checkpoint runs/v8_curriculum/01_static/seed_42/checkpoints/best_feasible.pt \
  --out runs/low_tail_reward_ablation_full \
  --stage full --variants baseline_pd_bc baseline_no_bc no_braking_pd_bc no_entry_velocity_pd_bc \
  --device cuda
```

A run directory is never overwritten. Use a new output root for a rerun.
